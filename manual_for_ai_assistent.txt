Функциональные требования к чатам и сообщениям

Juridical Assistant · Документ для согласования моделей и backend

Статус: согласованные функциональные решения + требования к
проектированию
Дата: 11 ноября 2026 года

  Назначение: описать, как должны работать чаты и сообщения, какие
  данные о них необходимо хранить и какие требования безопасности
  соблюдать. Документ предназначен для согласования между
  backend-разработчиком и разработчиком, который проектирует и реализует
  слой базы данных.

------------------------------------------------------------------------

1. Как должен работать чат

Сервис не требует регистрации. Посетитель получает анонимную
идентичность и может создавать несколько независимых чатов с юридическим
AI-консультантом.

Чаты и сообщения сохраняются между посещениями сайта. Пользователь может
вернуться позднее, открыть прежний чат и продолжить разговор. Каждый чат
имеет собственную историю: сообщения одного чата не должны случайно
попадать в контекст другого.

Согласованные правила:

-   Регистрация и пароль не нужны.
-   Пользователь идентифицируется анонимно.
-   Один пользователь может иметь несколько чатов.
-   История чатов сохраняется между посещениями.
-   У чатов и сообщений учитывается время создания; для изменяемых
    сущностей также учитывается время последнего изменения.
-   Отправленные сообщения редактировать нельзя.
-   Чат можно переименовать.
-   Чат можно удалить вместе с его сообщениями и связанной с ним
    памятью.
-   Название нового чата формируется автоматически на основе первого
    сообщения пользователя.

1.1. Жизненный цикл чата

1.  Пользователь впервые открывает приложение.
2.  Система создаёт или восстанавливает его анонимную идентичность.
3.  Пользователь создаёт чат.
4.  Пользователь отправляет сообщения и получает ответы AI.
5.  Чат и сообщения сохраняются.
6.  При следующем посещении пользователь снова получает доступ к своим
    чатам.
7.  Пользователь может открыть, продолжить, переименовать или удалить
    чат.

Важно: анонимный пользователь — это не временная сессия. Отсутствие
регистрации не означает, что история должна исчезать после закрытия
вкладки.

2. Какие данные нужны чату

Ниже перечислены функциональные поля, которые следует учесть при
проектировании модели чата. Это требования к данным, а не указание
конкретной реализации PostgreSQL или SQLAlchemy.

  -----------------------------------------------------------------------
  Поле / атрибут          Для чего нужно          Требование
  ----------------------- ----------------------- -----------------------
  id                      Уникально               Обязательно, уникальное
                          идентифицировать чат    значение

  owner_id                Определить, какому      Обязательно
                          анонимному пользователю 
                          принадлежит чат         

  title                   Показывать название в   Обязательно;
                          списке чатов            формируется
                                                  автоматически

  created_at              Знать, когда чат создан Обязательно

  updated_at              Сортировать чаты по     Обязательно
                          последней активности    
  -----------------------------------------------------------------------

Правила для чата

-   id не должен быть последовательным идентификатором, позволяющим
    легко перебирать чужие чаты. Предпочтителен UUID или другой
    непредсказуемый идентификатор.
-   owner_id связывает чат с анонимным владельцем.
-   При создании чат получает начальное название. После первого
    сообщения название автоматически формируется из его текста.
-   Пользователь может изменить название чата, но не может менять его
    владельца.
-   updated_at обновляется при добавлении нового сообщения и при
    переименовании чата.
-   Список чатов по умолчанию целесообразно показывать от недавно
    активных к старым.
-   Удаление чата должно удалять или делать недоступными все
    принадлежащие ему сообщения и связанные данные памяти. Конкретный
    механизм удаления выбирается разработчиком слоя хранения.

3. Какие данные нужны сообщению

Сообщение — это отдельная реплика внутри конкретного чата. В первой
версии есть только две роли: пользователь и AI-ассистент.

  -----------------------------------------------------------------------
  Поле / атрибут          Для чего нужно          Требование
  ----------------------- ----------------------- -----------------------
  id                      Уникально               Обязательно
                          идентифицировать        
                          сообщение               

  chat_id                 Определить чат, к       Обязательно
                          которому относится      
                          сообщение               

  role                    Понять, кто отправил    user или assistant
                          сообщение               

  content                 Хранить текст сообщения Обязательно

  status                  Отслеживать результат   Для сообщений AI
                          обработки               

  sources                 Хранить ссылки на       Для ответа AI; может
                          документы,              быть пустым
                          использованные в ответе 
                          AI                      

  created_at              Время создания          Обязательно
                          сообщения               

  updated_at              Время последнего        Желательно
                          изменения записи, если  
                          оно применимо           
  -----------------------------------------------------------------------

Правила для сообщения

-   Каждое сообщение принадлежит ровно одному чату.
-   Роль сообщения должна быть одной из двух: user или assistant.
-   После отправки текст сообщения не редактируется.
-   Сообщения одного чата должны иметь возможность выстраиваться в
    хронологическом порядке.
-   Время следует хранить в UTC с информацией о часовом поясе; при
    отображении его можно преобразовывать во время пользователя.
-   Сообщение пользователя сохраняется до начала генерации ответа, чтобы
    вопрос не терялся при сбое LLM.
-   Ответ AI должен быть связан с тем же чатом и сохраняться отдельно от
    пользовательского сообщения.
-   Для ответа AI необходимо сохранять источники, на которые он
    опирался, если они были возвращены компонентом RAG.
-   Системный промпт не является сообщением пользователя или ассистента
    и не должен автоматически добавляться в историю чата как обычная
    реплика.

3.1. Статусы обработки ответа AI

Для первой версии предлагается следующий набор статусов:

  Статус      Значение
  ----------- --------------------------------------------------
  pending     Ответ ожидает генерации или находится в процессе
  completed   Ответ успешно сформирован
  failed      При генерации произошла ошибка

Статус относится к обработке ответа AI. Пользовательское сообщение при
этом сохраняется.

Требование к повторной попытке: повторная генерация не должна создавать
дубликат исходного вопроса пользователя. Нужно определить, как именно
повторная попытка связывается с исходным запросом и где хранится
информация об ошибке. Это деталь реализации, которую следует согласовать
между backend и разработчиком хранения данных.

4. Источники в ответах AI

Юридический консультант должен по возможности показывать, на каких
документах основан ответ.

Для ответа AI предусматривается поле sources. Оно должно позволять
связать ответ с найденными материалами.

Предлагаемый состав одного источника для согласования:

  ---------------------------------------------------------------------
  Атрибут                            Назначение
  ---------------------------------- ----------------------------------
  document_id                        Идентификатор исходного документа

  document_title                     Название документа

  chunk_id                           Идентификатор найденного
                                     фрагмента, если он существует

  page                               Номер страницы, если доступен

  excerpt                            Короткий фрагмент текста, если его
                                     можно безопасно показывать

  url                                Ссылка на источник, если применимо
  ---------------------------------------------------------------------

Это предварительный контракт данных. Фактические поля должны
соответствовать тому, что возвращает RAG и что способен корректно
отобразить frontend. Не следует придумывать страницу или ссылку, если
источник их не предоставляет.

5. Безопасность и защита данных

В чате могут обсуждаться юридические обстоятельства и персональные
данные. Поэтому безопасность должна учитываться с самого начала.

5.1. Анонимная идентификация

-   Использовать криптографически стойкий случайный токен, а не простой
    счётчик или предсказуемую строку.
-   Не считать публичный chat_id секретом или доказательством владения
    чатом.
-   Хранить токен в cookie с HttpOnly; при HTTPS использовать Secure;
    подобрать SameSite с учётом архитектуры frontend.
-   Не передавать токен в URL.
-   Не записывать секретный токен в логи.
-   Проверять владельца чата на backend при каждой операции с ним.
-   При потере cookie пользователь может потерять доступ к анонимной
    истории. Восстановление доступа без регистрации требует отдельного
    продуктового решения.

5.2. Проверка доступа к чатам

Для каждого запроса, содержащего chat_id, backend обязан проверять, что
чат принадлежит текущему анонимному пользователю.

Это относится к операциям: - получить чат; - получить историю
сообщений; - отправить сообщение; - переименовать чат; - удалить чат.

Нельзя полагаться только на то, что frontend передал правильный
идентификатор.

При обращении к чужому или несуществующему чату API не должен раскрывать
содержимое переписки или сведения о владельце.

5.3. Валидация входных данных

-   Проверять, что текст сообщения не пустой после удаления пробелов.
-   Установить и проверять максимальную длину сообщения.
-   Проверять формат идентификаторов.
-   Проверять допустимые значения полей и статусов.
-   Не принимать роль сообщения от клиента как произвольное значение:
    пользовательский endpoint должен создавать сообщение с ролью user.
-   Не позволять клиенту самостоятельно создавать сообщения с ролью
    assistant.
-   Не позволять клиенту передавать или менять owner_id.
-   Ограничивать частоту запросов и размер входящих данных.

Конкретные числовые лимиты нужно согласовать отдельно.

5.4. Защита API и инфраструктуры

-   Использовать HTTPS в production.
-   Хранить секреты и ключи API в переменных окружения или
    секрет-хранилище, не в исходном коде.
-   Не коммитить .env и реальные ключи в Git.
-   Настроить CORS только для доверенных origin frontend.
-   Для cookie-аутентификации предусмотреть защиту от CSRF с учётом
    выбранной схемы запросов.
-   Не возвращать клиенту traceback, внутренние адреса сервисов,
    SQL-запросы и секретные параметры.
-   Логировать технические ошибки без записи токенов, паролей и лишнего
    содержимого юридической переписки.
-   Применять ограничения на размер запроса и защиту от чрезмерного
    числа обращений.

5.5. Удаление данных

При удалении чата пользователь ожидает удаления всей связанной с ним
истории и памяти.

Нужно обеспечить, чтобы после удаления: - чат больше не возвращался в
списке; - сообщения чата нельзя было получить через API; - связанные
векторные записи не использовались при поиске; - источники и
вспомогательные данные, принадлежащие только этому чату, не оставались
доступными через API.

Сроки удаления из резервных копий и технических журналов определяются
отдельной политикой хранения данных.
